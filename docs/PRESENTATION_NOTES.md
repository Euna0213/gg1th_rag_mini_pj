## A. 발표 스토리 후보 (한 줄 요약)
"RAG는 모델이 아니라 **검색**이 품질을 결정한다. 법률 구조를 살린 청킹으로 baseline을 만들고, 실패 사례를 찾아, 기법별로 실제 개선 여부를 수치로 검증했다."

## 발표 한계 항목 (근거가 약한 수치와 그 이유)
- 비용 절감(약 4~6배 추정): mini와 직접 비교하지 못함, 환산이 실제보다 45% 낮게 나왔음
- 검색 점수 0.96~1.0: 24문항(1문항=0.04), LLM 재정렬의 실행 간 흔들림
- 확인된 오류 1/24: 표시된 6개만 대조, 18개 미확인, 대조는 AI가 수행
- 관련성: 별도 평가 없이 정답성·검색 적중으로 갈음

## C. 설계 결정과 이유 (질문받으면 답할 것)
- **왜 조 단위 청킹?** 법률은 조가 의미 완결 단위이고 인용도 "제N조"로 한다. 고정 길이(예: 500자) 청킹은 조문을 중간에서 자른다.
- **왜 긴 조만 항 단위로 쪼갰나?** 조 전체를 넣으면 길어 임베딩이 흐려지고, 항은 독립된 규정이기 때문. 기준은 700자.
- **왜 청크 앞에 `[제N장 …]` 헤더를 붙였나?** 청크가 단독으로 검색돼도 어느 장·조인지 알 수 있고 임베딩에도 문맥이 들어간다.
- **왜 id를 (조, 항)으로?** 재실행해도 중복 저장되지 않는다.
- **왜 시스템 프롬프트에서 "조문에 없으면 모른다"를 강제?** RFP 핵심: LLM의 일반 지식이 아니라 검색 근거로만 답한다.

- **API vs PDF?** 검색 속도는 소스와 무관(Qdrant가 처리). 차이는 파싱 정확도뿐이다. 공식 API로 Docling 결과를 대조 검증했다 → 데이터 신뢰도를 수치로 말할 수 있다.

- **왜 평가를 조 단위로?** 한 조가 여러 청크(항)로 나뉘는데, 청크 단위로 순위를 매기면 같은 조의 항들이 상위를 차지해 지표가 왜곡된다. 사용자에게 보이는 단위도 "제N조"다.
- **Hit@K / Recall@K / MRR 쉬운 설명:** Hit@K = Top-K 안에 정답이 있나(예/아니오), Recall@K = 정답이 여러 개일 때 몇 %를 찾았나, MRR = 정답이 평균 몇 번째에 나오나(1위면 1, 2위면 0.5…).
- **Golden set 설계:** 25문항, 정의/일상어/숫자/세부/다중조문/범위 밖. 일부러 법률 용어가 아닌 일상어 질문을 넣어 임베딩의 의미 매칭을 시험. 정답은 원문을 읽고 근거를 note로 남김.

- **BM25란?** 질문의 단어가 문서에 얼마나 자주·특이하게 나오는지로 점수를 매기는 전통적 키워드 검색. Dense(의미 유사도)가 놓치는 "정확한 용어 일치"에 강하다.
- **RRF란?** Dense 점수(코사인)와 BM25 점수는 척도가 달라 직접 더할 수 없다. 대신 각자의 **순위**만 써서 1/(60+순위)를 더한다. 두 방법에서 모두 상위인 문서가 올라간다.
- **왜 한국어 토크나이저를 비교?** "인공지능은/인공지능을/인공지능의"처럼 조사가 붙어 공백 분리로는 같은 단어로 안 잡힌다. kiwi(형태소 분석)와 bigram(글자 2-gram)을 비교했더니 단독으로는 kiwi, Hybrid에서는 bigram이 MRR이 높았다.

- **왜 Reranker를 LLM으로?** 별도 모델 설치 없이 이미 있는 LLM API로 가능하고, 한국어 법률 문장의 의도를 이해한다. 단점은 호출당 지연·비용.
- **Reranker 흐름 한 줄 설명:** Hybrid가 후보 15개를 가져옴 → LLM이 "질문에 직접 답하는 정도" 0~10점 → 점수순 정렬 → 상위 5개를 답변 컨텍스트로 사용.
- **발표 스토리의 핵심 장면:** RFP 예시 질문 "고영향 인공지능이란?"이 Dense(실패) → 청킹 개선(실패) → BM25/Hybrid(4위) → Rerank(1위)로 개선되는 과정. 각 단계가 "무엇을 고쳤고 무엇이 남았는지"를 보여준다.

## D. 코드에서 발견한 주의점 (템플릿 `common/`)
- `common/ai_model.py` `get_llm_model()`이 인자(`model`, `api_key`)를 받고도 내부에서 상수 `MODEL`, `API_KEY`를 쓴다. 인자가 무시된다. 지금은 동작에 지장 없어 그대로 둠.
- `common/config.py`의 `LLM_TEMPERATURE` 기본값이 2(비정상적으로 높음)지만 코드는 `temperature=0` 인자를 써서 실제 영향은 없음. 이 값을 쓰는 코드가 생기면 문제가 된다.
- 기본 `max_tokens=512`는 답변이 잘릴 수 있어 파이프라인에서 1024로 올렸다.
