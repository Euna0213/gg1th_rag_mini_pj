# 진행 기록 (발표용)

> 프로젝트: 근거 기반 AI 기본법 QA 백엔드 (RAG Mini Project RFP)
> 원칙: 단계마다 **무엇을 / 왜 / 어떻게 / 결과·발견**을 기록한다. 발표자가 흐름을 이해할 수 있게 쓴다.

## 전체 흐름 (RFP)
`문서 로딩 → 구조 기반 청킹 → Qdrant 저장 → 검색 → 검색 개선 → 근거 기반 답변 → 평가`
- Offline: 문서를 검색 가능한 지식으로 만들기 (loader → chunker → vectorstore)
- Online: 질문에 필요한 근거를 찾아 답하기 (retriever → reranker → pipeline → API)

## RFP 체크리스트
| 항목 | 상태 |
|---|---|
| Docling으로 법률 문서 로딩 | 완료 (`rag/loader.py`) |
| 장·절·조·항 구조 확인 | 완료 |
| 구조 기반 Chunk + Metadata | 완료 (`rag/chunker.py`) |
| Embedding + Qdrant 저장 | 완료 (`rag/vectorstore.py`) |
| Dense Retrieval baseline | 완료 (`rag/retriever.py`) |
| 검색 개선 | 청킹 개선·BM25·Hybrid(RRF)·**LLM Reranking**·Multi Query(효과 없음) 완료 / Metadata Filtering은 생략 |
| Grounded Answer + Source (`POST /ask`) | 완료. 최종 구성(Hybrid kiwi + LLM Rerank) 연결·스모크 테스트 완료 |
| Golden set + Hit@K/Recall@K/MRR | 완료 (`eval/`), baseline 측정됨 |
| 답변 평가 (정답성·근거 충실성·환각) | 예정 |

## Step 0. 환경 (템플릿에서 제공)
- uv 단일 `.venv`를 notebook/app이 공유, `common/`(config, qdrant, ai_model) 공유 모듈, Qdrant는 docker로 실행.
- 설계 이유: 노트북에서 실험 → 검증된 코드를 `rag/`로 옮기고 `app/`이 그대로 import.

## Step 1. 데이터 확보
- 대상: 「인공지능 발전과 신뢰 기반 조성 등에 관한 기본법」(법률 제21311호, 시행 2026.7.21), 법제처 lsiSeq=282791.
- 시행: 법제처 페이지 본문이 AJAX로 로딩되어 curl로 수집 불가 → 브라우저에서 PDF로 직접 다운로드 → `data/ai_basic_law/`.
- 발견: 처음 받은 HWPX는 **시행령**이었다. 기본법(국회 제정, 원칙·골격)과 시행령(정부, 세부 기준)은 다른 문서. RFP 데이터는 기본법이므로 기본법 PDF 사용. 시행령은 선택 사항(추가 시 `doc_type` 메타데이터 필요).
- PDF 확인: 15쪽, 장 6개·절 2개·조 약 46개, 항 ①~⑭. 텍스트 추출 정상(OCR 불필요).

## Step 2. 문서 로딩 `rag/loader.py`
- 도구: Docling (RFP 요구).
- 문제: `export_to_markdown()`은 목록 번호를 다시 매겨 호/목이 깨진다 (예: "5. 가. …", "15. 카. …", 원래는 4호 아래 가~카목).
- 해결: 항목 단위(`doc.texts`)로 읽어 원문 번호(marker)를 보존. 쪽 머리글/바닥글(page_header/footer)과 반복 표제 제거.
- 결과: 408줄, 장·절 제목 온전, 호·목 번호 원문 그대로.
- 남은 문제: PDF 줄바꿈 때문에 "말 한다" 같은 어색한 공백 일부 존재 (검색에는 큰 영향 없음, 필요 시 정리).

## Step 3. 구조 기반 청킹 `rag/chunker.py`
- 단위: **조(條)** 가 기본. 법률은 조 단위로 의미가 완결되고 인용도 "제N조"로 하기 때문.
- 긴 조(700자 초과)는 **항(①②…)** 단위로 분할. 항이 없는 긴 조(제2조 정의, 약 1960자)는 정의 목록 특성상 그대로 둠.
- 각 청크 앞에 `[제N장 … > 제N절 …]` 문맥 헤더를 붙이고, 항 청크에는 조 제목도 붙여 단독으로 읽혀도 어느 조인지 알게 함.
- Metadata: `chapter`, `section`, `article`, `article_title`, `paragraph` → `/ask`의 `sources.article`에 사용.
- 결과: 47개 조(부칙 포함) → 94개 청크 (항 단위 청크 55개). 길이 중앙값 약 240자, 최대 1960자.

## Step 4. 임베딩 + Qdrant 저장 `rag/vectorstore.py`
- 컬렉션 `ai_basic_law`, 코사인 거리, 모델 `text-embedding-3-small`(common/config 기본값). 청크 94개 저장.
- 각 포인트의 payload = `text` + 메타데이터(장/절/조/제목/항) → 나중에 출처 표시와 Metadata Filtering에 사용.
- id를 (조, 항)으로 결정적으로 생성 → 재실행해도 중복 저장되지 않음.

## Step 5. Dense 검색 baseline 첫 확인 (정식 평가 전, 눈으로 확인)
| 질문 | 1위 | 판단 |
|---|---|---|
| 고영향 인공지능이란 무엇인가요? | 제33조 (고영향 AI의 확인) | **약점**: 정의가 있는 제2조는 3위 안에도 없음 |
| 생성형 인공지능 결과물 표시 의무 | 제31조 (투명성 확보 의무) | 적절 |
| 과태료는 얼마인가요? | 제43조 (과태료) | 적절 |

- 발견: RFP 예시 질문인 "고영향 인공지능이란?"에서 정의 조항(제2조)을 놓친다. 제2조는 정의 19개가 한 청크(약 1960자)라 임베딩이 희석되고, "고영향 인공지능" 제목이 붙은 제33~35조가 더 가깝게 잡힌 것으로 보인다.
- 개선 후보(가설, 실험으로 확인할 것): 제2조를 호 단위로 분할, BM25/Hybrid(정확한 용어 일치), Reranking, Multi Query.
- 이 사례를 개선 전/후 비교의 대표 예시로 쓴다.

## Step 6. Grounded Answer + `POST /ask`
- `retriever.py`: baseline Dense Top-5. 결과를 `Retrieved(text, score, metadata)`로 감싸고 출처 라벨 `제N조(제목) 항`을 만든다.
- `pipeline.py`: 검색된 조문을 `[1]..[5]`로 번호 매겨 Context 구성 → LLM. 시스템 프롬프트로 "참고 조문에 없으면 '확인할 수 없습니다'", "조 번호를 밝혀라", "쉬운 말로"를 강제.
- `app/main.py`: `POST /ask` → `{answer, sources:[{article, content}]}` (RFP 형식). uvicorn으로 실제 호출해 확인.

### 동작 확인 (baseline, 개선 전)
| 질문 | 결과 |
|---|---|
| 과태료는 얼마인가요? | 정답 (3천만원 이하, 제43조, 부과 사유까지 근거 제시) |
| 오늘 서울 날씨 알려줘 | 범위 밖 질문 → "제공된 조문에서는 확인할 수 없습니다" (환각 없음) |
| 고영향 인공지능이란 무엇인가요? | **오답에 가까움**: Top-5에 제2조(정의)가 없어 "정의를 확인할 수 없다"고 답하고 제33~35조만 설명 |

핵심 관찰: 답변 품질은 **검색 품질에 종속**된다. 프롬프트가 근거 밖 답변을 막아서 환각 대신 "모른다"로 안전하게 실패하지만, 사용자에게 필요한 답은 못 준다 → 검색 개선의 필요성이 명확.

## Step 7. 공식 Open API로 Docling 파싱 결과 검증 (`scripts/fetch_law_api.py`)
- 목적: PDF→Docling 파싱이 정확한지, 공식 데이터(국가법령정보 공동활용 API)와 대조해 확인. 로딩 자체는 RFP대로 Docling을 유지.
- 방법: `lawSearch.do`로 법령일련번호(MST 282791) 확인 → `lawService.do`로 본문 JSON 수집 → `data/ai_basic_law/law_api.json`. 키는 `.env`의 `LAW_OC`에서만 읽고 출력하지 않는다.
- 대조 결과 (조 단위):
  - 조 개수·번호: API 46개 = PDF 파싱 46개, **차집합 없음** (제17조의2, 제22조의2·3 같은 가지조문 포함)
  - 글자 구성(공백·순서 무시): **46개 중 40개 완전 일치**
  - 나머지 6개(제7·16·17의2·18·22의2·22의3조): PDF 쪽에만 `<신설 2026. 1. 20.>`, `<개정 …>` 같은 **개정 표기**가 더 있음. API에만 있는 글자는 0 → **누락 없음**
- 결론: Docling 파싱은 신뢰 가능. 유일한 차이는 개정 표기이며, 검색에는 노이즈일 수 있어 청킹 시 제거/메타데이터화를 검토(실험 후보).

## Step 8. Golden set + baseline 평가 (`eval/golden_set.jsonl`, `eval/evaluate.py`)
- Golden set: 25문항 = 검색 평가 24 + 범위 밖 1("서울 날씨", 답변이 "확인할 수 없음"이어야 함).
  - 질문 유형: 정의 2 / 일상어 9 / 숫자 3 / 세부 8 / 다중조문 2 (정답 조문이 2~3개) / 범위 밖 1
  - 정답은 **조(條) 단위**. 법령 원문을 직접 읽고 근거를 `note`에 적었다 (예: "제4조 1항 국외 행위도 국내 영향 시 적용").
  - 법을 모르는 사용자가 쓸 말투로 작성 (예: "외국 회사가 만든 AI도 적용받나요?").
- 평가 방식: 청크가 아니라 **조 단위**로 순위를 매김. 한 조가 여러 청크(항)로 나뉘어도 같은 조는 하나로 보고 처음 순위를 쓴다. (청크 단위로 하면 같은 조의 항들이 순위를 차지해 왜곡됨)
- 지표: Hit@K(Top-K 안에 정답이 하나라도 있나), Recall@K(정답 조문 중 몇 %를 찾았나), MRR(정답이 평균 몇 번째에 나오나의 역수 평균).
- 결과 저장: `eval/results/dense.json` (기법별 결과를 같은 형식으로 쌓아 비교).

### Baseline (Dense, text-embedding-3-small) 결과
| 지표 | 값 |
|---|---|
| Hit@1 / Hit@3 / Hit@5 | 0.833 / 0.833 / 0.917 |
| Recall@1 / @3 / @5 | 0.785 / 0.833 / 0.917 |
| MRR | 0.859 |

Top-5에서 놓친 질문 2개 (둘 다 **제2조 정의** 조항):
- "고영향 인공지능이란 무엇인가요?" → 제33·35·34·31·30조
- "인공지능사업자는 누구를 말하나요?" → 제18·26·32·31·24조

순위만 낮은 질문 2개:
- "서비스가 AI로 운영된다는 사실을 … 미리 알려야 하나요?" → 정답 제31조가 5위 (1위는 제13조)
- "한국에 사무소가 없는 해외 AI 기업은…" → 정답 제36조가 4위

### 해석
- Step 5의 가설("제2조는 정의 19개가 한 청크라 희석된다")과 일치하는 결과: **정의형 질문 2개가 모두 제2조를 놓침**. 제2조만 고치면 Hit@5가 0.917 → 1.0이 될 수 있다.
- 주의: Dense 하나로도 이미 높다. 법이 작아(46개 조) 검색 공간이 좁기 때문. 그래서 개선 기법의 효과는 **작게** 나올 것이고, 순위(Hit@1, MRR)와 정의형·일상어 질문에서 차이가 날 가능성이 크다. "효과가 크지 않았다"도 정직한 결과로 발표할 수 있다.
- 한계: 24문항은 표본이 작아 0.04 차이(= 1문항)는 우연일 수 있다. 개선 판단은 어느 질문이 바뀌었는지 함께 본다.

## Step 9. 개선 실험 ① 제2조 호 단위 분할 (`chunk_law(split_definitions=True)`)
- 가설: 제2조(정의)가 한 청크(약 1960자)라 임베딩이 희석되어 정의형 질문을 놓친다.
- 변경: 제2조만 호(1. 2. …) 단위로 분할. 목(가. 나. …)은 해당 호에 붙임. 각 청크에 "제2조(정의) 이 법에서 사용하는 용어의 뜻은…" 도입문을 붙여 단독으로도 의미가 통하게 함. 청크 94 → 105개(제2조 1 → 12).
- 공정한 비교를 위해 별도 컬렉션 `ai_basic_law_defsplit`에 저장 (baseline 컬렉션은 그대로).

| 지표 | baseline | ① 호 분할 | 변화 |
|---|---|---|---|
| Hit@1 | 0.833 | 0.833 | 0 |
| Hit@3 | 0.833 | 0.875 | +1문항 |
| Hit@5 | 0.917 | 0.958 | +1문항 |
| MRR | 0.859 | 0.873 | +0.014 |

### 질문별로 본 결과
- 개선: "인공지능사업자는 누구를 말하나요?"(q02) — 제2조 7호가 Top-5에 들어옴.
- **그대로 실패: RFP 예시 질문 "고영향 인공지능이란?"(q01).** 제2조 4호 청크가 Top-10에도 없음. 4호 청크는 정의 한 문장 뒤에 "에너지 공급, 먹는물 생산, 의료기기 …" 같은 영역 목록 10개가 붙어 길고, 질문과의 유사도 1~5위는 제목에 "고영향 인공지능"이 들어간 제33~35조가 차지.
- **부작용: "생성형 AI로 만든 결과물에는 표시를 해야 하나요?"(q15)가 악화.** 정답 제31조가 1위 → 2위. 이유: 분할로 생긴 작은 청크 "제2조 5호(생성형 인공지능 정의)"가 질문의 "생성형 AI"와 단어가 겹쳐 1위로 올라옴 (정의는 질문 의도 "표시 의무"와 무관).
- 해석: 청킹 개선은 일부는 고치고 일부는 해침 — **trade-off**. 지표 숫자(+1문항)만 보면 개선이지만, 가장 중요한 q01은 그대로고 q15는 나빠졌다. 실험으로 확인한 것: "제2조 희석"은 원인의 일부일 뿐, 4호에서는 **긴 목록이 정의 문장을 희석**하고 **제목에 용어가 들어간 조문이 유사도에서 유리**하다는 두 번째 원인이 있다.

### 다음 후보 (이 결과가 가리키는 것)
- Hybrid(BM25+Dense, RRF): 용어 일치를 강화하지만 "고영향 인공지능"이 제33~35조 제목에도 많아 q01은 안 풀릴 수도 있음 → 실험으로 확인
- Reranking: 질문 "무엇인가요(정의)"와 "정의 조항"의 의도 일치를 판단할 수 있어 q01, q15 모두 기대
- 4호 청크를 정의 문장 / 영역 목록으로 추가 분할(청킹 2차 개선)

## Step 10. 개선 실험 ② BM25 · Hybrid(RRF)
- BM25: 키워드(단어) 일치 기반 검색. Dense(의미)가 놓치는 "정확한 용어" 일치를 보완.
- Hybrid: Dense Top-20 + BM25 Top-20을 **RRF**로 결합. 점수 대신 순위만 쓰므로 척도가 다른 두 점수를 안전하게 합친다: score = Σ 1/(60 + rank).
- 구현: `rag/retriever.py`의 `retrieve_bm25`, `retrieve_hybrid`. BM25 인덱스는 Qdrant에 저장된 청크 텍스트로 만든다(Docling 재실행 불필요).
- 한국어 토크나이저 2종 비교: `kiwi`(형태소 분석, 명사·동사어근만) vs `bigram`(형태소 분석 없이 글자 2-gram). 한국어는 조사가 붙어("인공지능은", "인공지능을") 공백 분리만 하면 BM25가 잘 안 되기 때문.
- 도구: `eval/compare.py`로 모든 실험 결과를 한 표로 비교.

### 전체 비교 (24문항, MRR 순)
| method | Hit@1 | Hit@3 | Hit@5 | Recall@5 | MRR |
|---|---|---|---|---|---|
| hybrid_bigram_defsplit | 0.875 | 0.958 | 0.958 | 0.958 | **0.921** |
| hybrid_bigram | 0.875 | 0.917 | 0.958 | 0.958 | 0.913 |
| bm25_kiwi | 0.875 | 0.875 | 0.917 | 0.896 | 0.885 |
| hybrid_kiwi_defsplit | 0.833 | 0.917 | 0.958 | 0.938 | 0.883 |
| hybrid_kiwi | 0.833 | 0.875 | **1.000** | **0.979** | 0.876 |
| defsplit (① 제2조 분할, Dense) | 0.833 | 0.875 | 0.958 | 0.958 | 0.873 |
| dense (baseline) | 0.833 | 0.833 | 0.917 | 0.917 | 0.859 |
| bm25_bigram | 0.708 | 0.958 | 0.958 | 0.958 | 0.826 |

### 해석
1. **BM25 단독은 토크나이저에 크게 좌우**된다. kiwi는 Hit@1 0.875로 좋지만, bigram은 Hit@1 0.708로 가장 나쁘다(bigram은 "인공", "공지", "지능" 같은 조각이 거의 모든 조문에 있어 변별력이 낮음). 그런데 **Hybrid에서는 bigram이 오히려 MRR이 높다**: Dense가 1위를 잡아주고 BM25는 보조만 하기 때문.
2. **Hybrid는 Dense보다 대체로 낫다**: MRR 0.859 → 0.876~0.921. 가장 좋은 조합은 hybrid_bigram_defsplit(MRR 0.921).
3. **RFP 예시 질문 q01은 hybrid_kiwi(제2조 미분할)에서만 Top-5에 들어온다(4위)**. 제2조를 호 단위로 쪼갠 컬렉션(defsplit)에서는 오히려 다시 빠진다. 해석(가설): 미분할 제2조는 "고영향 인공지능"이 한 청크에 여러 번 나와 BM25 점수가 높은데, 분할하면 용어 빈도가 흩어진다. **실험 ①(청킹 개선)과 ②(BM25)가 서로 상충**한다는 뜻.
4. **우승자가 없다**: Hit@5 최고(hybrid_kiwi 1.0)와 MRR 최고(hybrid_bigram_defsplit 0.921)가 다른 조합이다. q01은 어느 조합에서도 1위가 되지 못했다(최고 4위).

### 주의 (정직하게)
- 24문항에서 1문항 = Hit 0.042, MRR 차이도 수 문항의 순위 변동에 불과하다. 조합 간 차이(0.87~0.92)는 **통계적으로 유의하다고 말하기 어렵다**.
- 토크나이저(kiwi/bigram)를 같은 golden set으로 골랐으므로 그 선택은 약간 낙관적이다(과적합 가능성). 최종 수치를 말할 때는 "이 24문항에서의 결과"라고 한정한다.
- 확실한 것: (a) Dense 단독보다 Hybrid가 안정적으로 낫다, (b) 어떤 방식이든 "고영향 인공지능이란?"을 1위로 만들지 못했다 → 검색 방식이 아니라 **질문 의도(정의형)와 조문 성격(정의 조항)의 연결**이 필요하다 → Reranking 실험의 동기.

## Step 11. 개선 실험 ③ LLM Reranking (`rag/reranker.py`)
- 아이디어: 1차 검색(Hybrid)이 후보를 넓게 가져오면, LLM이 후보를 읽고 "이 조문이 질문에 직접 답하는가"를 0~10점으로 매겨 재정렬. 임베딩/BM25는 단어·의미 유사도만 보지만 LLM은 **질문의 의도**를 이해한다.
- 구현: Hybrid Top-15 후보를 한 번의 LLM 호출로 채점(후보당 600자까지) → 점수 내림차순, 동점은 1차 순위 유지. JSON 파싱 실패 시 1차 순서 그대로 사용(안전장치).
- 프롬프트는 일반 기준만 사용(10=답이 그대로 있음, 5=일부/간접, 0=단어만 겹침). 특정 평가 질문에 맞춘 힌트는 넣지 않았다(과적합 방지).

### 결과
| method | Hit@1 | Hit@3 | Hit@5 | Recall@5 | MRR |
|---|---|---|---|---|---|
| rerank_kiwi (2회 실행) | 0.958 / **1.000** | 1.000 | 1.000 | 1.000 | 0.972 / **1.000** |
| rerank_bigram_defsplit | 0.958 | 1.000 | 1.000 | 0.986 | 0.979 |
| rerank_bigram | 0.958 | 0.958 | 0.958 | 0.958 | 0.963 |
| (비교) 최고 Hybrid: hybrid_bigram_defsplit | 0.875 | 0.958 | 0.958 | 0.958 | 0.921 |
| (비교) baseline Dense | 0.833 | 0.833 | 0.917 | 0.917 | 0.859 |

### 해석
1. **Reranking이 가장 큰 개선**: MRR 0.859(Dense) → 0.921(최고 Hybrid) → 0.96~1.0(Rerank). Hit@1이 0.83 → 0.96~1.0. Hybrid까지 개선폭은 1~2문항 수준이었지만 이번에는 Hit@1 기준 3~4문항이 올라가 우연이라고 보기 어렵다.
2. **RFP 예시 질문 q01("고영향 인공지능이란?")이 해결됨**: 모든 검색 방식이 못 풀었던 질문인데 rerank_kiwi에서 제2조가 1위(LLM 점수 10점). Hybrid가 제2조를 후보 안(4위)에 넣어주고, LLM이 "이 질문의 답은 정의 조항"이라고 골라냈다 → **1차 검색은 후보를 넓게(recall), 재정렬은 정확하게(precision)**라는 역할 분담이 실제로 확인됨.
3. **재정렬은 후보 안에서만 고를 수 있다**: rerank_bigram은 q02에서 제2조가 후보 15개에 들어오지 못해 실패. 1차 검색이 후보에 못 넣으면 LLM도 못 살린다. 같은 이유로 `rerank_bigram_defsplit`은 q01을 2위로 둔다.
4. **실행마다 결과가 흔들린다**: 같은 설정(rerank_kiwi)을 두 번 돌렸을 때 q02 하나가 달라 MRR이 0.972 ↔ 1.000. 점수는 temperature 0이어도 LLM 출력이 완전히 같지 않다. 따라서 "1.000"을 대표 성능으로 말하지 말고 **0.96~1.0 범위**로 말한다.
5. **비용**: Reranking은 질문당 LLM 호출 1회가 추가되고 입력이 후보 15개(약 6천 자)라 질문당 수 초가 더 걸린다. 평가 4가지 설정×24문항에 약 10분이 걸림. 정확도와 지연/비용의 trade-off.

### 주의
- 24문항, 같은 모델로 채점 구성 → 과대평가 가능. 실제 서비스 성능으로 일반화하지 말고 "이 24문항에서의 비교"로 한정.
- 이제 점수가 천장(1.0)에 가까워 golden set으로는 더 구별이 안 된다. 추가 개선을 보려면 더 어려운 질문(모호한 질문, 여러 조문 종합)이 필요.

## Step 12. 개선 실험 ④ Multi Query (`retrieve_multiquery`, `expand_queries`)
- 방법: LLM이 질문을 3개의 다른 표현으로 바꿈 → 원 질문과 함께 각각 Hybrid 검색 → RRF로 합침. 목적은 1차 후보의 recall을 높여 Rerank가 못 살린 q02류(후보에 정답이 없는 경우)를 줄이는 것.
- 결과 (같은 24문항):

| 비교 | Multi Query 없음 | Multi Query 있음 |
|---|---|---|
| Hybrid kiwi (MRR / Hit@5) | 0.876 / 1.000 | 0.882 / 0.917 |
| Hybrid bigram (MRR / Hit@5) | 0.913 / 0.958 | 0.906 / 0.958 |
| Hybrid kiwi + Rerank (MRR / Hit@5) | 0.972~1.000 / 1.000 | 0.963 / 0.958 |

- 해석: **Multi Query는 효과가 없었다.** 어떤 조합에서도 일관되게 좋아지지 않았고(MRR 변화 −0.009~+0.006), Rerank와 함께 쓰면 오히려 약간 낮았다. 이유(가설): 변형 질문이 “…의 정의는 무엇인가요?”처럼 원 질문과 거의 같은 말이라 새 후보를 거의 더하지 못하고, RRF에서 원 질문과 같은 방향의 표가 중복되어 노이즈가 늘어남. 질문당 LLM 호출이 1회 늘고 Hybrid 검색이 4배라 비용·지연만 증가.
- 결론: 최종 구성에서 **제외**. “시도했고 효과가 없었다”는 RFP가 요구한 “실제로 개선되는지 확인”에 해당하는 정직한 결과.
- 참고: 마지막 재실행(mq_rerank_kiwi_run2)은 API 키 크레딧 한도 초과(HTTP 402, MonoRouter 30,000 소진)로 중단. 결과 파일 없음.

## Step 13. 최종 구성 연결 (`rag/pipeline.py`)
- 최종 검색: Hybrid(BM25 kiwi + Dense, RRF) 후보 15개 → LLM Rerank → 상위 5개 → 답변. `RETRIEVAL = {"mode": "kiwi", "multi_query": False}`로 한 곳에서 설정.
- Metadata Filtering은 생략: 법이 작고(46개 조) 질문이 장에 딱 떨어지지 않아 장 판별 오류 위험이 이득보다 크다고 판단. 실험하지 않았음을 명시한다.
- 스모크 테스트 (연결 직후):
  - “고영향 인공지능이란 무엇인가요?” → 소스 1위가 제2조(정의)이고, 답변이 제2조제4호를 근거로 정의와 해당 영역을 설명. (연결 전에는 “정의를 확인할 수 없다”였음)
  - “오늘 서울 날씨 알려줘” → “제공된 조문에서는 확인할 수 없습니다.” (환각 없음)

## Step 14. API 호출 디스크 캐시 (`rag/cache.py`)
- 목적: 크레딧 소진 재발 방지. 같은 입력이면 API를 다시 호출하지 않는다.
- 적용 지점 4곳: 질문 임베딩(`embed`), Rerank 채점(`rerank`), Multi Query 변형(`expand`), 답변 생성(`answer`). 저장 위치 `.cache/<종류>/<해시>.json` (이미 .gitignore 대상).
- 키 설계: 프롬프트·모델 이름·질문·컨텍스트 전체의 해시. 프롬프트나 모델을 바꾸면 키가 달라져 낡은 결과를 쓰지 않는다.
- 안전장치: 실패한 결과(JSON 파싱 실패 등)는 저장하지 않아 나쁜 결과가 굳지 않는다. 임시 파일에 쓴 뒤 교체해서 중단돼도 깨진 파일이 남지 않는다.
- 주의: **같은 설정의 실행 간 흔들림(재현성)을 재려면 `RAG_CACHE=0`으로 끈다.** 캐시를 켜면 두 번째 실행은 첫 실행의 LLM 응답을 그대로 재사용하므로 흔들림이 0으로 보인다.
- 검증: 가짜 LLM/임베딩으로 호출 횟수를 세어 확인(API 호출 없음). 같은 입력은 1회만 호출, 다른 입력은 새로 호출, 파싱 실패는 미저장, RAG_CACHE=0은 매번 호출, 프로세스 내 캐시를 비워도 디스크 캐시로 호출 0회.
- 한계: 캐시 도입 전의 평가는 저장돼 있지 않아 **첫 실행은 한 번 비용이 든다.** 이후 같은 평가의 재실행은 비용이 0이다.

| 범위 밖 질문(서울 날씨) 거절 | 통과 |

- 정답성 2점 17개, 1점 5개, 0점 1개(q02), 1점이 나온 질문: q01, q09, q10, q21, q24.
- q02(“인공지능사업자는 누구를 말하나요?”): 검색이 제2조를 놓쳤고, 답변은 지어내지 않고 “정의를 확인할 수 없다”고 거절. 정답성 0점이지만 환각은 아님 → 근거 기반 설계가 의도대로 동작.

### 판정의 신뢰성 문제 (중요)
- 원문과 직접 대조한 결과, 환각으로 표시된 **q18과 q21의 답변은 실제로는 정확**했다 (제34조제1항 각 호, 제40조제1항 2호 등 원문과 일치).
- 원인: 판정자에게 보여준 근거를 조문당 **350자로 잘라서**, 제34조 호 4~6처럼 뒤쪽 내용을 못 본 채 “근거에 없다”고 판정. 판정 설계의 실수.
- 따라서 환각률 0.25는 **상한(과대평가)** 이며 실제는 더 낮다. 진짜 오류로 확인된 것은 q01의 조문 번호 형식 오류(“제2조제1호4목”, 원문 구조는 제2조제4호) 정도.
- 또한 판정자와 답변 모델이 같은 작은 모델이고 사람 검토가 없다. 이 수치는 “참고 지표”로만 말한다.
- 미확인: q09, q10, q24의 1점/환각 표시도 같은 이유일 가능성이 있으나 아직 원문과 대조하지 않았다.

### 수동 대조 결과 (크레딧 0, 재판정 대신)
환각/낮은 점수로 표시된 6개(q01, q09, q10, q18, q21, q24)의 답변을 원문 조문과 직접 대조했다.

|---|---|---|

- 결론: 판정자가 환각으로 표시한 6개 중 **실제 오류는 q01의 인용 형식 오류 1건**, 나머지 5개는 판정자의 오판(근거를 350자로 잘라 보여준 탓).
- 보정한 수치: 확인된 오류 1/24 ≈ **0.04** (판정자 원값 0.25). 발표에서는 “판정자 0.25 → 원문 대조 후 확인된 오류 1건(조문 번호 형식)”으로 설명한다.
- 한계: 대조는 표시된 6개에만 했다. 표시되지 않은 18개는 판정자 점수(2/2/0)를 그대로 썼고 직접 확인하지 않았다. 대조는 사람이 아니라 Claude가 했다. 발표자가 몇 건을 직접 원문과 대조해 보면 더 좋다.
- 재판정은 하지 않기로 결정: 남은 크레딧(약 7,500)을 11월 6일까지 다른 프로젝트에도 써야 하므로, 약 290~1,100크레딧이 드는 재판정 대신 무료 수동 대조를 택함.

### 오류 기준과 직접 대조 (발표자 확인)
- 기준: 법률 서비스에서는 조문 번호가 정확해야 하므로 **내용이 맞아도 조문 번호 표기가 틀리면 오류로 센다.**
- 확인된 오류 1건 (q01의 “제2조제1호4목”) → 확인된 오류율 1/24 ≈ 0.04. 내용 오류는 0건.
- 발표자가 q18, q21을 원문과 직접 대조해 정확함을 확인(판정자의 오판 재확인). q01은 위 표기 기준을 적용.

### RFP 대조 결과와 결정
- 충족: Docling 로딩, 구조 기반 청킹·메타데이터, Qdrant 저장, Dense baseline, BM25·Hybrid·RRF·Reranking·Multi Query 구현과 비교, Metadata Filtering 제외(필수 아님, 이유 명시), 근거 기반 답변·`POST /ask`(최종 구성으로 HTTP 호출 확인), Golden set·Hit@K·Recall@K·MRR, 답변 평가(정답성·근거 충실성·환각).
- **빠진 것: 관련성(relevance) 평가.** RFP는 정답성·관련성·근거 충실성·환각 4가지를 제시했으나 판정에는 3가지만 넣었다(설계 누락).
- 결정: 크레딧을 아끼기 위해 **관련성은 별도로 평가하지 않고 정답성과 검색 적중(23/24)으로 갈음**하며, 발표에서 이 사실을 명시한다. 추가 판정(약 290~1,100크레딧)은 하지 않는다.
- 사람 검증: `scripts/show_answer.py qNN`으로 답변과 원문을 나란히 보며 발표자가 직접 몇 건 대조한다.

## Step 17. 챗봇 UI (`app/main.py`, `app/static/`)
- 요구: 첨부한 디자인 이미지대로 FastAPI로 챗봇 서비스 구현. 3단 구성(왼쪽 대화 목록 | 가운데 채팅 | 오른쪽 근거 문서).
- 구조: 프런트엔드는 빌드 도구 없이 `index.html` + `style.css` + `app.js`(바닐라 JS)를 FastAPI가 정적 파일로 서빙. 기존 `POST /ask` 계약은 그대로 두고(`{question}` → `{answer, sources}`), UI용으로 `GET /api/article?article=제34조`를 추가했다.
- `GET /api/article`: 청크(항 단위)로 나뉜 조를 항 순서대로 이어 붙여 원문 전체를 돌려준다. Qdrant 조회만 하므로 LLM·임베딩 크레딧이 들지 않는다. 항 청크마다 붙여둔 “제N조(제목)” 접두어와 문맥 헤더는 한 번만 보이도록 정리.
- 화면 기능: 새 대화/최근 대화(선택·삭제, 브라우저 localStorage 저장), 사용자 말풍선+시간, 답변 카드(굵게·목록·제목 렌더링), 복사하기, 다시 생성하기, 참고 근거 목록(펼치기 + “원문 보기 ↗” → 오른쪽 패널에 조문 전체), 추천 질문 칩, 입력창, 로딩 표시, 오류 카드(+다시 시도), 반응형(1180px 이하 근거 패널 서랍식, 820px 이하 사이드바 서랍식).
- 설계 결정:
  - 답변은 먼저 전부 HTML 이스케이프한 뒤 허용한 서식(굵게·목록·제목)만 다시 만든다 → LLM 출력의 HTML/스크립트가 실행되지 않음.
  - 한글 입력 조합 중 Enter는 전송하지 않는다(IME 처리).
  - “다시 생성하기”는 저장된 답변을 무시하고 새로 생성한다(`regenerate=true`, `cache.cached(refresh=True)`). Rerank 결과는 캐시를 그대로 쓰므로 LLM 호출은 답변 생성 1회.
  - 서버 오류 메시지는 원인 범주(크레딧 부족, 호출 상한, 일반 오류)만 사용자에게 보여주고 상세는 서버 로그에만 남긴다.
  - 첨부(클립)는 디자인에 있으나 기능이 없어 비활성 표시(“준비 중”).
  - 추천 질문 첫 칩은 평가에 쓴 질문 문구(“고영향 인공지능이란 무엇인가요?”)를 그대로 써서, 저장된 답변이 있어 크레딧 없이 열린다. 디자인 이미지의 문구(“고영향 AI란 무엇인가요?”)와는 다르다.
- 예시 질문 더 보기(크레딧 0): 평가 때 답변이 저장된 질문 15개를 “예시 질문 더 보기”로 노출. 저장된 25개 질문 모두 네트워크 호출 없이 열리는 것을 호출을 막은 상태로 검증(25/25). 검색이 실패했던 q02는 데모에서 제외. 질문 문구가 한 글자라도 다르면 저장된 답을 쓰지 못하므로 골든셋 문구 그대로 사용.
- 한계: 대화 기억이 없다. RAG는 질문 하나씩 독립적으로 처리하므로 “그럼 그건?” 같은 후속 질문은 이해하지 못한다. 대화 목록은 브라우저별(localStorage)로만 저장된다.
- 검증(크레딧 사용 0): ① 서버 엔드포인트(`/`, 정적 파일, `/api/article`, 404, 빈 질문 422, 저장된 질문 `/ask`) ② jsdom에서 가짜 서버 응답으로 34개 동작 검사(전송, 마크다운 렌더, 이스케이프, 원문 보기, 복사, 다시 생성, 오류·오프라인, 대화 저장·삭제, 칩, IME) 전부 통과 ③ 헤드리스 Chromium 스크린샷으로 데스크톱·모바일(400px) 화면 확인, 콘솔 오류 없음, 모바일 가로 넘침 없음.
- 실행: `uv run uvicorn app.main:app --reload` → http://localhost:8000
- 비용 주의: 처음 보는 질문 1개는 Rerank 1회 + 답변 1회(nano 모델 기준 약 50크레딧)가 든다. 같은 질문은 캐시가 있어 무료. “다시 생성하기”는 매번 답변 생성 1회가 든다.
